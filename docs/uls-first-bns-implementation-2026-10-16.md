# Первый продуктовый этап: ULS → SLS при подборе БНС

Дата: 2026-10-16. Расчётная применимость: исследовательская, **не готовый расчёт КЖ**.

## Контракт

Обычная программа `pile_rebar.py` принимает:
- `loads`: расчётные сочетания N–Mx–My для **ULS нормального сечения**, с уже сформированными по проекту коэффициентами нагрузок. Python учитывает отдельно заданный случайный эксцентриситет там, где его применение согласовано.
- `sls_probe.loads`: **нормативные/сервисные** сочетания N–Mx–My (полные и длительные составляющие) для проверки трещин. Это отдельный массив, не тот же набор усилий, что ULS.
- `force_basis: {"uls":"design","sls":"normative"}`: обязательное явное подтверждение семантики входных наборов, когда запрошен SLS. Само по себе наличие этих меток **не гарантирует**, что пользователь загрузил верные значения и коэффициенты.
- `sls_probe.short_materials`, `long_materials`: отдельные экспериментальные материалы второй группы, требующие независимой проверки методики и конкретного проекта.

В обычной обвязке принудительно устанавливается `sls_execution_policy=uls_pass_only`. Из внешнего JSON пользователя нельзя включить `research_all` через эту программу.

## Алгоритм отбора по кандидату

1. Проверить геометрию и расстановку продольных стержней.
2. Рассчитать **все** сочетания ULS по N–Mx–My. Для каждого должны быть выполнены численная сходимость, конечность и взаимная согласованность коэффициента запаса и использования (`factor×utilization≈1`).
3. Если есть неизвестный результат ULS, принять статус `indeterminate`; **не считать это доказанным отказом по прочности**. SLS пропустить со статусом `not_evaluated_uls_indeterminate`.
4. Если ULS определён, но хотя бы одно сочетание не проходит, кандидат `fail_uls`. **Не рассчитывать SLS**; отметить `not_evaluated_uls_fail`. Это нормальная причина отказа конкретного варианта армирования.
5. Только если все ULS сочетания успешно пройдены, запустить `CrackWidthSolver` для нормативных SLS усилий. Возвращать оригинальную уточнённую методику CScore и консервативный предварительный вариант; сохранять `NOT_VERIFIED` до независимой проверки в АРБАТ.
6. Предварительное предложение армирования допустимо только при прохождении ULS и всех исследовательских SLS сочетаний. Случаи `engineering_review`, `preliminary_exceeds_limit`, `indeterminate` не допускаются автоматически.

## Поля JSON-ответа

В `cases[*]`:
- `status`: `pass_uls`, `fail_uls` или `indeterminate`;
- `sls_gate`: `calculated_uls_pass`, `skipped_uls_fail`, `skipped_uls_indeterminate`;
- `sls_status`: `preliminary_below_limit`, `preliminary_exceeds_limit`, `engineering_review`, `research_indeterminate`, `not_evaluated_uls_fail` или `not_evaluated_uls_indeterminate`;
- `sls_probe=null` при пропуске; отсутствие числового результата не равно 0 мм или PASS.

На верхнем уровне: `uls_case_ids`, `sls_case_ids`, `force_basis` и `force_basis_note=user_declared_not_independently_verified`.

## Отдельные исследования CScore

`tools/cross_section_sls_matrix.py` и `tools/run_crack_research.py` отправляют **явно** `sls_execution_policy=research_all`, поскольку исторический эксперимент сравнивал ширины с АРБАТ при dummy ULS нагрузке. Этот режим сохранён только для отдельного стенда и в выходных данных помечен как `calculated_research_override`. В рабочем подборе он запрещён.

Это важно: восемь ранее неопределённых по раскрытию сечений действительно не проходят ULS в **независимых отчётах АРБАТ**, но из фиктивного ULS загружения в исторической матрице нельзя автоматически вывести такой же статус в CScore. Не удалять эти негативные тесты и не превращать их результаты в 0 мм.

## Ограничения и продолжение

- ULS сейчас проверяет только **прочность нормального сечения**, не всю конструкцию: нет полного расчёта поперечной силы, анкеровки, конструктивных требований, геотехнической несущей способности свай, общей устойчивости и других необходимых проверок.
- SLS пока исследовательский; расчёт с разной полной/длительной N не реализован в pinned OpenCS. Предварительная зона `±3%` около K=1 — эвристика направления на проверку, не нормативный запас.
- Параметры `force_basis` заявляются пользователем; связь конкретных расчётных и нормативных сочетаний не вычисляется и не доказывается автоматически.
- Прямоугольные сечения уже поддерживаются как **одно явное исследовательское расположение стержней в C#**, но выбор армирования стены в грунте и двух рабочих граней ещё требует отдельной реализации. Нельзя считать эту задачу готовой после ULS-first.

## Проверка

Добавлены контрактные тесты на согласованность ULS/SLS, отказ ULS, неопределённость ULS и недопустимость одобрения при пропуске. Workflow оставлен **ручным**; следующий запуск должен проверить:
- проходящий ULS с реальным расчётом SLS;
- заведомо перегруженную БНС с `sls_probe=null` и правильной причиной;
- неизменность независимой 70-случайной матрицы и сравнений с АРБАТ;
- отсутствие регрессии 486 upstream тестов.

Изменения пока **не были проверены новой Windows CI**.
