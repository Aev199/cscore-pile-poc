# CScore → автоматический перебор армирования БНС (эксперимент, v0.1)

**Задача:** не писать свой модуль СП 63, а попробовать использовать отдельное ядро **CScore** из проекта [OpenCS](https://github.com/rumata-ap/OpenCS) для *пакетной* проверки готовых сочетаний `N, Mx, My` и вариантов продольного армирования круглой сваи.

**Статус (15.10.2026):** Windows-версия CScore успешно собиралась в GitHub Actions (последняя подтверждённая сборка [38716913205](https://github.com/Aev199/cscore-pile-poc/actions/runs/38716913205)); проведены независимые сравнения по нормальному сечению с АРБАТ. Новая версия Python с автоматическим случайным эксцентриситетом и механизмом контроля upstream внесена в репозиторий, но **ещё не проверена Windows CI**.

**Не применять для выдачи КЖ.** Прототип проверяет только прочность нормального сечения методом нелинейной деформационной модели (НДМ); полный набор нормативных проверок *не выполнен*. Нет расчёта по наклонным сечениям, раскрытию трещин, анкеровке/стыкам, полной проверке конструктивных требований, устойчивости/второму порядку (`η`). Не проверены выбор материалов и нормативных коэффициентов, применимость результатов PLAXIS, модель длительных нагрузок, погрешность аппроксимации круга и независимая точность CScore.

## Что уже умеет прототип

1. Принять несколько **совместно действующих** наборов усилий (стадии/глубины/сочетания) — без произвольного сочетания независимых экстремумов.
2. Построить варианты `число стержней × диаметр × поворот` для одной БНС.
3. Отбросить физически не помещающиеся варианты по *предварительной геометрической* проверке зазоров. Это **не** нормативная проверка всех расстояний по СП 63.
4. Передать модели в CScore через небольшое .NET-приложение, которое обращается **непосредственно** к `LimitForceSolver.ForCrossSection(...).AllFactor(N,Mx,My)`; собственной формулы прочности нет.
5. Вернуть JSON/CSV с коэффициентом использования и статусом по каждому набору усилий.
6. Пометить несходимость, пропуск или испорченный результат как `indeterminate`, **никогда не** как успех.
7. Показать самый лёгкий **предварительный** вариант среди `pass_uls` (это не готовое решение для КЖ).

## Как запустить без установки тяжёлого расчётного ПО

### Вариант А: GitHub Actions (для получения Windows EXE)

1. Создай отдельный репозиторий на GitHub и положи туда файлы **этой папки**.
2. Открой **Actions → CScore pile PoC Windows → Run workflow**. Запуск только ручной, чтобы не расходовать минуты при каждом коммите.
3. После завершения открой артефакт **cscore-pile-windows** — в архиве будет `CScorePileRunner.exe`, пример исходных данных и первые реальные численные результаты, **только если сборка и прогон прошли успешно**.
4. На рабочем ПК достаточно Python, .NET SDK и OpenCS устанавливать не надо: опубликованный EXE должен содержать необходимые компоненты .NET. Совместимость такой упаковки с бинарными зависимостями CScore **нужно подтвердить сборкой и запуском**.
5. Запуск рядом с EXE из командной строки: `python pile_rebar.py demo_bns.json --runner CScorePileRunner.exe`. Будут сформированы `results/pile_results.json` и `results/pile_results.csv`.

### Вариант Б: машина разработчика с Git + .NET 10 SDK

```powershell
./scripts/setup.ps1
python -m unittest discover -s tests -v
python pile_rebar.py examples/demo_bns.json --runner publish/CScorePileRunner.exe
```

Для запуска через DLL: `python pile_rebar.py examples/demo_bns.json --runner путь/к/CScorePileRunner.dll` (требуется установленный .NET runtime). **На рабочем корпоративном ПК не нужно запускать скрипт сборки.**

## Формат примера

`examples/demo_bns.json`:

- `pile`: диаметр БНС, защитный слой до внешней грани хомута/спирали, диаметр этой поперечной арматуры, минимальный геометрический просвет, параметры дискретизации сечения.
- `materials`: **явно заданные** расчётные характеристики материалов; это демонстрационные числа, а не автоматически выбранные нормативные значения.
- `loads`: совместно действующие `n_kn`, `mx_knm`, `my_knm`, идентификатор комбинации. **CScore: N отрицательная при сжатии**, положительная при растяжении. Остальные знаки и оси необходимо верифицировать при импорте PLAXIS.
- `search`: разрешённые числа и диаметры стержней, повороты полярной раскладки.

Единицы: **мм** для размеров и диаметров, **кН**, **кН·м**, **кПа** для материалов (как в исходных API CScore). Внутри CScore геометрия переводится в метры. Коэффициент использования `utilization = 1 / factor`; значения, полученные без сходимости, не принимаются.

Код сейчас не оптимизирован по скорости и последовательно считает все варианты. Первый приоритет — надёжность расчётного контракта, а не производительность.

## Случайный эксцентриситет в обычном подборе (новое)

В `pile_rebar.py` учёт случайного эксцентриситета задаётся **явно**. В режиме `sp63_stat_determinate` (только статически определимая схема) для сжимающей продольной силы N менее нуля добавляется момент с `ea=max(L0/600,D/30,10 мм)`. Результирующий добавочный момент направлен вдоль вектора (Mx, My) исходного сочетания. Это гипотеза, валидированная для одноосных испытаний АРБАТ; для двухосных случаев требуется отдельная верификация.

Пример (см. `examples/demo_bns.json`):

```json
"eccentricity": {
  "mode": "sp63_stat_determinate",
  "static_scheme": "statically_determinate",
  "effective_length_mm": 3000
}
```

При центральном сжатии Mx=My=0 нельзя автоматически выбрать наиболее неблагоприятную ориентацию. Задай `zero_moment_axis` из `mx_positive`, `mx_negative`, `my_positive`, `my_negative` — **или программа остановит расчёт с ошибкой**.

Альтернативы: `{"mode":"already_in_loads"}` — если моменты **уже включают** необходимую поправку; `{"mode":"research_none"}` — для исследовательского сравнения без неё. При отсутствии блока сохранена совместимость со старыми JSON, но результаты помечаются как неполные и `selected_uls_candidate` не выдаётся. Не нужно добавлять поправку дважды. В JSON (`forces_audit`) и CSV записываются как исходные N/M, так и эффективно проверенные N/M и приращение момента.

Пока не учтены геометрическая нелинейность, общая устойчивость и полный расчёт второго порядка `η`. Наличие eₐ не заменяет эти проверки и не делает результат готовым КЖ.

## Трещиностойкость в самом ядре CScore

**Она поддерживается в upstream**, хотя наш `CScorePileRunner` пока её не вызывает. В библиотеке есть общий `CrackWidthSolver` (для `CrossSection`, теоретически применим к круглой геометрии и косому изгибу) и специализированный `Sp63CrackWidthChecker` (прямоугольник и тавр, круглое сечение прямо отклоняется). Реальная интеграция требует отдельных SLS усилий, длительной/кратковременной частей, правильных N/NL характеристик материалов и обязательного контроля сходимости. В pinned upstream `CrackWidthSolver` иногда возвращает результат с нулевой шириной при **несходимости**; поэтому вывод `PassedLong=true` нельзя принимать как самостоятельное доказательство трещиностойкости. См. `docs/upstream-and-crack-width.md`.

## Обновления OpenCS/CScore

Версия исходников зафиксирована в `config/opencs.lock.json`. Еженедельный workflow `Check upstream CScore updates` смотрит изменения в `CScore/`, тестах и математических зависимостях; при наличии релевантных изменений обновляет **одну GitHub Issue**. Он не меняет SHA и не запускает тяжёлую Windows сборку.

Для перехода на новую версию: создать отдельную ветку, изучить изменения, обновить lock и все источники pin SHA, запустить CI, сверить результаты АРБАТ (в том числе пограничный Ø800 T08), убедиться в отсутствии новых несходимостей и только затем перенести обновление в основную ветку. На рабочем Windows-ПК SDK не требуется.

## Экспериментальная трещиностойкость БНС

Появился **отдельный исследовательский пробник**, не влияющий на ULS-подбор и не заменяющий АРБАТ. Он вызывает настоящий upstream `CrackWidthSolver` для двух круглых сечений — Ø800/12Ø25 и Ø1000/16Ø28 — и сравнивает экспериментальные результаты с `отчет_800_v2.rtf` и `отчет_1000_v2.rtf`.

В Windows CI автоматически запускается:

```powershell
python tools/run_crack_research.py --runner publish/CScorePileRunner.exe --output-dir results/crack_probe
```

Результаты сохраняются в `crack_probe/crack_width_comparison.csv` и парных исходных/расчётных JSON. **Никакие коэффициенты из этого исследования не учитываются при выборе продольного армирования.** Материалы для SLS и равенство длительной и полной части нагрузки — пока явно обозначенные экспериментальные допущения, а не доказанная эквивалентность АРБАТ. Часть скрытых проблем сходимости upstream всё ещё требует доработки. Подробнее: `docs/crack-probe-v1.md`.

## Сопоставление раскрытия трещин с АРБАТ

По девяти сопоставимым загружениям найден конкретный источник различий:
OpenCS с июля 2026 использует напряжение арматуры **сразу после**
образования трещины при определении ψs. Ранее бралось дотрещинное
состояние, что приводило к большему ψs и, соответственно, большему
расчётному раскрытию. Никаких изменений в исходную проверенную методику
upstream мы не вносим.

Экспериментальная диагностика дополнена двумя независимыми способами:
1. Исторический вариант **до трещинообразования** только для исследования
   причин расхождения, не как установленная методика АРБАТ.
2. Допускаемый п.8.2.15 СП63 вариант **ψs=1** — консервативная
   предварительная проверка, без численной подгонки.

По уже полученным девяти случаям ψs=1 даёт среднее отклонение
9.05% для Ø800 и 12.92% для Ø1000, против 25.4% и 32.1%
у исходного CScore. Разногласия «CScore проходит, АРБАТ не проходит»
исчезают на этом наборе; появляется одно заведомо консервативное
расхождение при Ø1000 T02. **Это не верификация полного SLS**.

Документация: `docs/crack-arbat-compatibility.md`. Новые сравнительные
численные поля будут проверены только следующей Windows CI-сборкой.

## Развитие SLS: основной консервативный и альтернативный авторский метод

С учётом инженерного решения пользовательский основной метод предварительной
проверки трещин — `arbat_conservative`. Он использует проверяемую гипотезу
напряжения арматуры до трещинообразования, **но не выдаёт результат меньше**
исходного авторского CScore. Если сравнение неприменимо (например, разная
полная и длительная доля изгиба), применяется отдельная консервативная
предварительная проверка по `ψs=1`, без произвольных коэффициентов.

По явному выбору пользователя `"preliminary_method": "native_refined"`
основным результатом становится исходная уточнённая методика автора.
Она **не ошибочна**, и её оригинальное численное значение всегда сохраняется.
Изменения не затрагивают исходный OpenCS.

Значения около единицы, включая `0.989` и `1.014`, для **предварительного
отбора** попадают в `engineering_review` при `"review_band":0.03`.
Это наша эвристика маршрутизации на проверку инженером, а не допустимое
нормативное отклонение. В рабочую документацию автоматически не выпускается
ни один из этих вариантов без полного контрольного расчёта.

Проверка трещин остаётся дополнительным **исследовательским** блоком
`sls_probe`; `pile_rebar.py` принимает его опционально и сохраняет отдельно
от расчёта прочности. Пример: `examples/verification/P800_sls_preselection_example.json`.

Развёрнутая методика: `docs/cross-section-sls-research-v2.md`.

## Уточнение исследования SLS: трещины только при полной нагрузке

Для ситуаций, когда `Mдлит ≤ Mcrc < Mполн`, уточнённое ядро OpenCS
ранее завершало расчёт с нулевым значением до проверки полного действия.
Наш C#-адаптер теперь **в отдельной исследовательской ветке** повторно
вызывает неизменённый CScore при полной нагрузке и извлекает только
кратковременную составляющую `Acrc2` с `φ1=1`. Для частичных
нагружений этот результат **не становится автоматическим допуском**:
выводится `crack_solver_path=supplemental_full_load_Acrc2` и
`engineering_review` или `preliminary_exceeds_limit`.

Возможные разнонаправленные моменты и несходимость дополнительного
решения остаются неопределёнными. Для других 8 случаев с ранним
нулевым результатом отчёты АРБАТ независимо показывают превышение
прочности по предельному моменту (коэффициенты 1.36–1.76). Это
важная диагностическая информация, но **не доказанная причина** отказа
численного решателя. Никаких вымышленных значений ширины там нет.

Описание и критерии следующей сборки: `docs/sls-short-only-investigation-2026-10-16.md`.
Изменения требуют новой Windows CI-проверки — результат 59/70 пока
является последним численно подтверждённым.

## Решение по оставшимся восьми несходимостям

[Последний проверенный Windows CI](https://github.com/Aev199/cscore-pile-poc/actions/runs/38872918563)
подтвердил: 70 Python тестов и 486 OpenCS тестов, из 70 SLS-сочетаний
59 исходных расчётных результатов, 3 исследовательских расчёта только
кратковременной ширины и 8 `indeterminate`. Для **всех 8**
вторичный StrainSolver также не сошёлся. Независимый АРБАТ показывает
на этих конкретных восьми вариантах превышение несущей способности
по ULS (K=1.36–1.76). **Не тратим дополнительные усилия на их
численную сходимость SLS**, пока не обнаружена такая же ошибка на
пригодных по прочности сечениях. Эти испытания сохраняются как
негативные регрессионные тесты без ложного допуска.

Следующий продуктовый конвейер: подтверждённый ULS на **расчётных**
нагрузках → SLS на **нормативных** нагрузках только для ULS-пригодных
кандидатов. ULS_FAIL ≠ SLS=0: при отказе по прочности отмечаем
`SLS_NOT_EVALUATED_ULS_FAIL`. Сейчас это **архитектурное решение**,
а не внедрённая логика; историческая 70-случайная матрица содержит
лишь dummy ULS. Подробнее:
`docs/uls-first-sls-scope-decision-2026-10-16.md`.

## Первый рабочий шаг: ULS → SLS для вариантов армирования БНС

Реализовано условное выполнение расчёта раскрытия трещин: **сначала все
расчётные сочетания ULS, затем нормативные SLS только для кандидатов,
прошедших прочность нормального сечения**. При ULS_FAIL либо ULS_INDETERMINATE
дорогой SLS-расчёт не запускается; отчёт содержит причину
`not_evaluated_uls_fail` или `not_evaluated_uls_indeterminate`.
Пропуск не означает нулевое раскрытие или пригодность.

При запросе SLS обвязка требует явное
`"force_basis":{"uls":"design","sls":"normative"}` и сохраняет
раздельные идентификаторы сочетаний, но сами усилия и коэффициенты
нагрузок **не верифицирует**. Для обычного подбора установлен
`sls_execution_policy=uls_pass_only`. Старые независимые исследования
АРБАТ могут применять `research_all` только как отдельный, явно
помеченный режим с dummy ULS, а не как обход проверок для рабочего
армирования.

В CI добавлена реальная проверка перегруженной БНС и сохранены тесты
на независимую 70-случайную матрицу. **Последние изменения ещё не
проверены Windows CI**, сборки автоматически не запускаются.

Подробности: `docs/uls-first-bns-implementation-2026-10-16.md`.
Следующий этап после проверки — прикладные варианты армирования
прямоугольных секций стены в грунте, арматура по рабочим граням,
конструктивная валидация и отдельная программа необходимых ULS/SLS.

## Стена в грунте: одинаковые каркасы и усилия на метр

Добавлен отдельный `wall_rebar.py`. Принимает 1–3 одинаковых каркаса на
захватку и независимо перебирает стержни двух рабочих граней. Сохраняет
As/м, эквивалентный шаг и реальные координаты стержней; проверяет заданные
геометрические просветы. Усилия задаются на метр, сжатие N отрицательное.

```powershell
python wall_rebar.py wall_cages.json --preview
python wall_rebar.py wall_cages.json --runner CScorePileRunner.exe
```

В исходном репозитории пример расположен в `examples/wall_cages.json`.
В выходных `results/wall_results.json` и `.csv` есть определяющие сочетания
и предварительные варианты по ULS и ULS+SLS. Пример материалов и усилий
иллюстративный — не готовое задание для конкретного проекта.

Чтобы не округлять дробное число стержней на метр, ядро получает
равномерно армированную полосу шириной захватки, с усилиями, умноженными
на её ширину в метрах. Только N и Mx, один ряд на каждой грани.
Локальное раскрытие между каркасами эта усреднённая модель не проверяет.
SLS остаётся исследовательским. Подробности: `docs/wall-cage-selection.md`.

В ручной Windows workflow добавлены проверки настоящим ядром: полосы
1/3м при одинаковом As/м, оба знака момента, несимметричные грани,
отказ по ULS с пропуском SLS. **Новая Windows-проверка ещё не выполнена.**

## Локальный интерфейс «Сечения»

В Windows-архив добавлен `start_workbench.bat`: запускает локальное
приложение на Python и открывает его в браузере. Для интерфейса не нужны
дополнительные пакеты. Существующий CScore EXE используется для расчётов.

Первый сценарий: ручная таблица / вставка Excel либо чтение PLAXIS Output →
эпюры N/M/Q → подбор по отметкам → фон и участки усиления → ручное
редактирование и повторная проверка. Сохраняется JSON-проект. Для стены
выводятся две грани; для БНС — кольцо. Дополнительные стержни пока того же
диаметра, что и фон. Границы участков можно менять числами и перетаскиванием.

PLAXIS подключается через `plxscripting` среды PLAXIS. Импорт на живом
PLAXIS 2D v22.01 ещё требует проверки. Масштаб Embedded Beam задаётся явно
по таблице Output, поскольку Bentley менял его в 2023.1. Для БНС из Plate
погонные усилия умножаются на шаг свай один раз.

Инструкция: `docs/workbench-guide.md`. Пример при открытии иллюстративный.
Проверка Q, анкеровки/обрыва и полного конструктивного оформления не
реализована; SLS остаётся исследовательским. Новый сценарий интерфейса
включён в ручной Windows workflow; его реальный численный прогон ещё впереди.

Слой подбора каркасов стены подтверждён Windows run **38889852523**:
88 Python + 486 upstream тестов; ULS 1м/3м = 0.16540518 в обоих случаях.
Эта проверка предшествует интерфейсному модулю и не подтверждает его целиком.
