# CScore → автоматический перебор армирования БНС (эксперимент, v0.1)

**Задача:** не писать свой модуль СП 63, а попробовать использовать отдельное ядро **CScore** из проекта [OpenCS](https://github.com/rumata-ap/OpenCS) для *пакетной* проверки готовых сочетаний `N, Mx, My` и вариантов продольного армирования круглой сваи.

**Статус:** Python-часть и её защитные тесты запускаются. Численная часть на CScore **пока не собрана и не запускалась в текущем окружении**: здесь нет .NET SDK и интернета для загрузки исходников. Workflow для настоящей сборки и прогона предоставлен, но его результат **не подтверждён**.

**Не применять для выдачи КЖ.** Прототип проверяет только прочность нормального сечения методом нелинейной деформационной модели (НДМ); полный набор нормативных проверок *не выполнен*. Нет расчёта по наклонным сечениям, раскрытию трещин, анкеровке/стыкам, полной проверке конструктивных требований, устойчивости/второму порядку (`η`). Не проверены выбор материалов и нормативных коэффициентов, применимость результатов PLAXIS, модель длительных нагрузок, погрешность аппроксимации круга и независимая точность CScore.

## Что уже умеет прототип

1. Принять несколько **совместно действующих** наборов усилий (стадии/глубины/сочетания) — без произвольного сочетания независимых экстремумов.
2. Построить варианты `число стержней × диаметр × поворот` для одной БНС.
3. Отбросить физически не помещающиеся варианты по *предварительной геометрической* проверке зазоров. Это **не** нормативная проверка всех расстояний по СП 63.
4. Передать модели в CScore через небольшое .NET-приложение, которое обращается **непосредственно** к `LimitForceSolver.ForCrossSection(...).AllFactor(N,Mx,My)`; собственной формулы прочности нет.
5. Вернуть JSON/CSV с коэффициентом использования и статусом по каждому набору усилий.
6. Пометить несходимость, пропуск или испорченный результат как `indeterminate`, **никогда не** как успех.
7. Показать самый лёгкий **предварительный** вариант среди `pass_uls` (это не готовое решение для КЖ).

## Как запустить без установки тяжёлого расчётного ПО

### Вариант А: GitHub Actions (для получения Windows EXE)

1. Создай отдельный репозиторий на GitHub и положи туда файлы **этой папки**.
2. Открой **Actions → CScore pile PoC Windows → Run workflow**. Запуск только ручной, чтобы не расходовать минуты при каждом коммите.
3. После завершения открой артефакт **cscore-pile-windows** — в архиве будет `CScorePileRunner.exe`, пример исходных данных и первые реальные численные результаты, **только если сборка и прогон прошли успешно**.
4. На рабочем ПК достаточно Python, .NET SDK и OpenCS устанавливать не надо: опубликованный EXE должен содержать необходимые компоненты .NET. Совместимость такой упаковки с бинарными зависимостями CScore **нужно подтвердить сборкой и запуском**.
5. Запуск рядом с EXE из командной строки: `python pile_rebar.py demo_bns.json --runner CScorePileRunner.exe`. Будут сформированы `results/pile_results.json` и `results/pile_results.csv`.

### Вариант Б: машина разработчика с Git + .NET 10 SDK

```powershell
./scripts/setup.ps1
python -m unittest discover -s tests -v
python pile_rebar.py examples/demo_bns.json --runner publish/CScorePileRunner.exe
```

Для запуска через DLL: `python pile_rebar.py examples/demo_bns.json --runner путь/к/CScorePileRunner.dll` (требуется установленный .NET runtime). **На рабочем корпоративном ПК не нужно запускать скрипт сборки.**

## Формат примера

`examples/demo_bns.json`:

- `pile`: диаметр БНС, защитный слой до внешней грани хомута/спирали, диаметр этой поперечной арматуры, минимальный геометрический просвет, параметры дискретизации сечения.
- `materials`: **явно заданные** расчётные характеристики материалов; это демонстрационные числа, а не автоматически выбранные нормативные значения.
- `loads`: совместно действующие `n_kn`, `mx_knm`, `my_knm`, идентификатор комбинации. **CScore: N отрицательная при сжатии**, положительная при растяжении. Остальные знаки и оси необходимо верифицировать при импорте PLAXIS.
- `search`: разрешённые числа и диаметры стержней, повороты полярной раскладки.

Единицы: **мм** для размеров и диаметров, **кН**, **кН·м**, **кПа** для материалов (как в исходных API CScore). Внутри CScore геометрия переводится в метры. Коэффициент использования `utilization = 1 / factor`; значения, полученные без сходимости, не принимаются.

Код сейчас не оптимизирован по скорости и последовательно считает все варианты. Первый приоритет — надёжность расчётного контракта, а не производительность.
